# Adaptive Software Change

1. Inspect repository instructions and `git status`; preserve unrelated changes.
2. Identify a GitHub issue only from explicit task metadata, `ticket #N`, `issue #N`, or an `/issues/N` URL. Fetch its canonical identity with the authenticated GitHub connector; never infer one. Compute the ticket branch with `awf github branch "<issue title>" --issue-number <N> [--type <type>]`; never invent or normalize the branch name yourself.
3. Read the GitHub publication reference for issue work. The connector is mandatory for every GitHub capability it exposes. Never require, install, authenticate, or probe `gh` merely because the task targets GitHub; use it only as a targeted fallback for one demonstrably missing connector capability.
4. Prepare or reuse the AWF-generated branch before editing and never work directly on the configured base branch. A non-canonical branch may be reused only when it is a legacy ticket branch that already has the ticket PR; record that state explicitly as `legacy_reused`. Otherwise create/switch to the canonical AWF branch without force-push and without creating a competing PR.
5. Run `awf --mode auto sync <repo>`, retrieve strictly bounded task context with `awf context`, recall relevant positive and negative memory, and start an episode containing the issue, branch, and base-branch metadata.
6. State acceptance criteria and the stop budget, then make the smallest coherent change. Do not broaden the file scope to compensate for uncertain context.
7. Run canonical validation only through `python -m agentic_workflow.validation --all --repository <repo>`. The runner discovers the canonical commands itself, executes those exact commands, classifies failures and, only for a declared recoverable environment failure, executes `.agent/setup-project.sh` then retries the exact failed command within the retry budget. Never invoke a canonical gate directly, substitute a manual/ad-hoc equivalent, search for another venv/interpreter, or use a tool found opportunistically elsewhere in the workspace.
8. A `functional_failure` or `environment_failure_blocking` is a blocking validation result. Stop before publication with its precise cause. Do not install arbitrary tools inferred from free-form error text. Record the canonical command, executed command, setup decision, retry count, classification, and final result reported by AWF.
9. After validations pass, synchronize the Repository Brain again, inspect the complete diff, preserve unrelated work, scan for secrets, and verify the staged files and intended Conventional Commit.
10. Immediately before commit/push/PR, recompute the expected branch with the same `awf github branch` command and compare it to the active branch. Refuse publication on a mismatch unless the selected branch is the explicitly recorded `legacy_reused` branch with an already existing PR.
11. For a GitHub ticket, local implementation is never completion. Create the Conventional Commit with `Refs #N`, push the verified ticket branch, create or reuse the PR against the configured base branch, and verify the issue relationship. Retrieve GitHub's live default branch immediately before PR composition and use `Closes #N` only when the PR base is that default branch.
12. Record GitHub publication metrics on the episode before finishing it, including commit SHA/count, push, PR number/URL, expected and active branch, branch status, publication attempts, PR reuse and issue-link verification. Record complexity and every measured CI duration through `awf episode telemetry`; leave unavailable nullable measures missing. Then call `awf episode finish <episode-id> --outcome success ...`. AWF must reject `success` for an issue episode while validation has failed or commit/push/PR/link requirements are incomplete.
13. Run `awf episode payload <episode-id>` after the final episode update. Treat its `comment` value as opaque machine-readable data. With the authenticated GitHub connector, list top-level PR conversation comments, locate the single comment beginning `<!-- awf-telemetry:v1`, then update that comment in place or create it when absent. Never use `gh` for this transport, never create a second reserved comment on a retry, and stop on multiple pre-existing reserved comments. Do not publish task text, source, diffs, logs, prompts, environment variables or secrets alongside this comment.
14. Report separate `implementation_status`, `validation_status`, `publication_status`, `telemetry_status`, and `stop_reason`. Use `completed / passed / pr_created|pr_reused / created|updated|unchanged / completed` only after the verified PR and telemetry comment exist; otherwise report `blocked` or `incomplete`.
15. Never stop solely because `gh` is absent when the connector covers the task. Never merge by default, never force-push, never bypass protection, and never invent absent metrics.
